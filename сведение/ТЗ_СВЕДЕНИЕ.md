# ТЗ на сведение единиц темы в ядра

ЗАДАЧА: собрать из единиц одной темы ядра (канонические утверждения) с оговорками, приёмами, примерами и полным паспортом источников. Это сборка пазла из кусочков, вытащенных с официальных страниц Google про генерацию картинок (Nano Banana / Gemini image). Только чтение входа и запись одного файла результата. Без интернета. Не трогать ничего вне /root/БАЗА_ПРАВИЛ/исходники_кандидаты/сырьё/google/сведение/темы/. Не заходить в /root/.claude, /root/АВТОЗАВОД, /root/СИСТЕМА_ЗАВОДА, /root/БАЗА_ПРАВИЛ/data, rule_engine. Скрипты — только в своей подпапке scratchpad.

ВХОД: файл /root/БАЗА_ПРАВИЛ/исходники_кандидаты/сырьё/google/сведение/вход/тема_<тема>[__чN].jsonl. Поля единицы: код (E-<стр>-<n>), вид, утверждение_en, цитата (укорочена до 160 знаков; полная цитата лежит в /root/БАЗА_ПРАВИЛ/исходники_кандидаты/сырьё/google/извлечение/страницы/стр_<стр>.json по коду — открывать при необходимости), раздел, модели, применимость, сила, как_получено, дата_ед, заметка, стр, url, заголовок, дата_стр, ранг (1 доки/карточка модели, 2 ноутбук/codelab, 3 блог Google, 4 справка/продукт, 5 прочее), ранг_имя, _дд (единица длинной дистанции).

МОДЕЛИ: gemini-3-pro-image = Nano Banana Pro; gemini-3.1-flash-image = Nano Banana 2; gemini-3.1-flash-lite-image = Nano Banana 2 Lite; gemini-2.5-flash-image = Nano Banana (оригинальный, до 2026-02). Ключи: pro, nb2, lite, nb25, other (2.0 flash, Imagen и т.п.), не_указано. «Не указано» разрешается только по явным признакам страницы: страница или раздел посвящены конкретной модели; ссылка на анонс конкретной модели; дата публикации до февраля 2026 при названии «Nano Banana» без версии = nb25 (но НЕ если страница одновременно называет и Pro). Без признака остаётся не_указано, не гадать. Все решения писать в поле разрешение_моделей.

ШАГИ:
1. Прочитать ВСЕ единицы входа. Сгруппировать в кластеры «об одном и том же» независимо от вида: факт из карточки, приём из ноутбука, ограничение из доков, пример из блога — в один кластер, если про одно утверждение.
2. На каждый кластер — ЯДРО с полями:
   - код: Я-<тема>-<часть>-<n>
   - класс: правило_промпта | формула_шаблон | факт_лимит | ограничение_модели | возможность_модели | процедура | параметр_вызова | продукт | политика
   - подтема: короткое имя кластера
   - ядро_en: одно каноническое утверждение по-английски, самая точная и свежая формулировка из источников, без додумок. Формулы и шаблоны промптов — ДОСЛОВНО по-английски, слоты в квадратных скобках. Списки примеров-терминов от Google переносить дословно, не расширять своими.
   - составное: true, если правило состоит из обязательных частей (формула + спутники, набор из N правил, данных вместе); части: список. Составное не резать на атомы.
   - модели: {pro, nb2, lite, nb25, other, не_указано} с содержанием по каждой, где отличается
   - оговорки: [{модели, текст_en, из: [коды]}] — исключения и уточнения, прикреплённые к ядру
   - приёмы: [{текст_en, из: [коды]}] — как делать на практике
   - примеры: [коды единиц вида пример_промпта]
   - сила: как у лучшего источника: требование | рекомендация | возможность | факт. Осторожные слова Google («can», «try», «may») сохраняются, не усиливать. Если гайд говорит одно, а официальные примеры делают иначе — сила «рекомендация» и запись в противоречия с правилом «гайд-против-примера».
   - применимость: промпт | параметры_вызова | продукт | политика
   - ситуация_в_промпте: черновик «когда правило нужно» языком автора промпта: что видно в задаче или тексте промпта. НЕ пересказ самого правила.
   - не_применяется_когда: «тема похожа, а случай не тот»
   - магнит: true, если в ядре/оговорках есть отрицания, списки запретных слов или конкретные предметы из примеров Google (яблоко, окно, тюль), которые при конвертации в правило завода надо будет перевести в позитив/класс. Формулировки НЕ менять, только флаг.
   - термины: термины Google в ядре с тем значением, что на этих страницах
   - источники: ВСЕ единицы кластера: {код, стр, url, дата (дата_ед или дата_стр), ранг, фрагмент цитаты}; лучший_источник (самый высокий ранг, при равенстве — самая свежая дата, среди единиц, формулирующих само утверждение); дата_последняя
   - противоречия: [{суть, версии: [{текст, код, дата, ранг}], решение, правило_решения}]. Правила решения, применять по порядку: (а) модель — сначала разнести по моделям; (б) дата — новее побеждает, старое остаётся «заменено» (штампы «Last updated», различающиеся на день-два, датой не считать); (в) ранг — доки/карточка выше ноутбука, ноутбук выше блога, блог выше справки/продукта; (г) опечатка — цифра верна, если есть на двух независимых страницах, одиночная аномалия «опечатка источника»; (д) гайд-против-примера — правило из явного утверждения, сила понижается, факт нарушения примерами записывается; (е) текст-против-кода — правило из прозы, код остаётся примером; (ж) продукт-против-api — не сводить, разные области. Если ни одно не решает — статус «спор», обе версии сохраняются.
   - статус: согласовано | решено_по_правилу | один_источник | выведено (только из единиц «выведено» экстрактора) | спор
   - связи: [{с: код ядра этой части, тип: требует | конфликтует | уточняет}]
3. ПОЛНЫЙ УЧЁТ: каждый код единицы входа должен попасть хотя бы в одно ядро (источники/примеры/оговорки/приёмы) либо в список не_сведено с причиной (дубль по тексту другого кода / не относится к теме / слишком общее / слова не Google). Единица может стоять в двух ядрах, если несёт два утверждения. Проверить скриптом.
4. СЛОВАРЬ ТЕРМИНОВ части: [{термин, значение по этим страницам, где встречается, разночтения между страницами}].
5. МАТРИЦА ПО МОДЕЛЯМ, если тема содержит числа/лимиты/поддержку: [{параметр, pro, nb2, lite, nb25, коды по ячейкам, расхождения}].
6. Ничего не выдумывать: у каждого утверждения в ядре и оговорках есть код-источник. Выводы экстрактора (как_получено = «выведено…») в ядро попадают только со статусом «выведено».

РЕЗУЛЬТАТ: /root/БАЗА_ПРАВИЛ/исходники_кандидаты/сырьё/google/сведение/темы/<тема>[__чN].json — валидный JSON:
{"тема", "часть", "единиц_на_входе", "ядра":[…], "матрица_моделей":[…], "словарь_терминов":[…], "разрешение_моделей":[…], "не_сведено":[{"код","причина"}], "вопросы":[…], "сводка":"3–5 строк"}
После записи проверить скриптом: JSON валиден, все коды входа учтены, у каждого ядра есть источники и лучший источник входит в них, все связи ведут на существующие ядра.

ОТЧЁТ (коротко): единиц на входе, ядер, спорных, не_сведено (сколько и почему), противоречий по правилам решения, матрица моделей в 5–8 строк (если есть), 10 самых важных ядер одной строкой каждое, вопросы. Содержимое ядер сверх этого не пересказывать.
