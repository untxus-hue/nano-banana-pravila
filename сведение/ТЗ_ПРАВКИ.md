# ТЗ на правки сшитой темы по итогам проверки (шаг 4б)

ЗАДАЧА: взять сшитую тему и применить к ней всё, что нашли проверяющие и проход поперёк, по единым линиям ниже. Результат — исправленная тема в новой папке и журнал каждой правки. Файлы в сведение/сшито/, сведение/темы/, сведение/проверка/, сведение/поперёк/ НЕ менять. Без интернета. Ничего не выдумывать: каждая правка опирается на замечание проверяющего, предложение поперёк, линию из этого ТЗ или цитату из извлечение/страницы. Непонятно — не править, записать в вопросы.

ВХОД для темы <тема>:
- сведение/сшито/<тема>.json — сама тема (канон полей — сведение/ТЗ_СШИВКА.md, прочитать).
- сведение/проверка/<тема>.json — вердикты и проблемы по каждому ядру, слияниям, спорам, не_сведено.
- сведение/поперёк/предложения_статусов.json — взять записи по кодам этой темы.
- сведение/поперёк/реестр_споров.json — записи, где есть коды этой темы.
- сведение/поперёк/дубли_между_темами.json — группы, где есть коды этой темы.
- сведение/поперёк/разбор_сомнений_А.json и, если есть, разбор_сомнений_Б.json — пункты по этой теме.
- сведение/проверка/ОТЧЁТ_ПРОВЕРКИ.md — раздел темы и «Общий итог».
- сведение/темы/<тема>__чN.json (или <тема>.json), сведение/темы/другое.json — части до сшивки: для размерджа и восстановления потерянного.
- извлечение/страницы/стр_<стр>.json — полные цитаты по E-кодам.
- сведение/ТЗ_СВЕДЕНИЕ.md — правила а–ж, ключи моделей, классы.

ВЫХОД:
- сведение/исправлено/<тема>.json — тема в той же канонической форме (ТЗ_СШИВКА) плюс новые поля ядра: слой ("промпт" | "инструкция" | "справка"), дом ({тема, код} — где ядро живёт по дубли_между_темами; если дом — эта тема, то {тема: <тема>, код: свой код}).
- сведение/исправлено/<тема>_журнал.json — список правок: {код, поле, было, стало, основание: {вид: "проверка"|"предложения_статусов"|"реестр_споров"|"дубли"|"разбор_сомнений"|"линия", ссылка: id или код или номер линии}, решение: "применено"|"отклонено", почему (если отклонено или если правка неочевидна)}. КАЖДАЯ проблема из файла проверки и КАЖДОЕ предложение статуса по теме должны иметь запись в журнале, даже если отклонены.

ЕДИНЫЕ ЛИНИИ (решения Димы и координатора; применять ко всем ядрам темы, не только к отмеченным проверяющим):
Л1. Модели. «да» у модели только по явному признаку: страница или раздел о модели; ссылка на анонс модели; идентификатор модели в коде или таблице; единица со страницы, посвящённой модели. «Not supported / not optimized / not available» у модели → «нет». Общий источник на несколько моделей без явного перечня → «не_сказано». Правило со страницы про одну модель на другие не переносить, если Google не говорит прямо, что оно действует и для них. Модель по умолчанию в коде ноутбука — не признак. «Nano Banana» без версии после 02.2026 — не_указано. Старая gemini-2.5-flash-image (nb25) — отдельная модель, её ядра сохраняются с моделью nb25 и пометкой в примечание «gemini-2.5-flash-image shuts down 2026-10-02 (Gemini API)».
Л2. Выведенное. Единицы с как_получено «выведено» и единицы длинной дистанции не могут держать статус «согласовано». Если ядро держится только на них → статус «выведено», сила не выше «рекомендация», в примечание «derived from Google examples, not stated by Google». Если пример Google показывает правило, которое Google сказал прямо в другом ядре → пример прикрепить к тому ядру (поле примеры), а выведенное ядро убрать в не_сведено с причиной «пример правила <код>» (в журнал). Шаблоны со слотами, которых у Google нет (проверяющий: «слоты придуманы») → класс правило_промпта, статус выведено, сила рекомендация, текст без придуманных слотов, а конкретные промпты Google дословно в примеры.
Л3. Imagen. Ядра, где Imagen (любой версии), его параметры или рекомендации стоят как действующие → действует:false, заменено: {чем: "", почему: "Imagen retired 2026-08-17 (E-228-3, E-228-4); Gemini API E-1-177", коды: [...]}. Ядро не удалять.
Л4. Сила. «требование» только при must / never / only / required / do not / cannot в словах Google. should / try / consider / we recommend / for best results → «рекомендация». can / supports / lets you / allows → «возможность». Утверждение факта → «факт». Бывшие «приёмы», которым сшивка подняла силу без слов Google → вернуть «возможность».
Л5. Платформы. Gemini API, Vertex / Agent Platform, Firebase, приложения (Gemini app, Workspace, Flow и т.д.) — такой же признак, как модель. Никогда не сливать; расхождение между платформами → разнести по платформам (расширенное правило а), статус решено_по_правилу с примечанием «by platform», обе версии в противоречия с кодами. Спор остаётся только там, где расходятся источники одной платформы.
Л6. Копии одной страницы по разным URL — один источник. Статус «согласовано», который держится только на копиях, → «один_источник».
Л7. Магнит. true только там, где в порождающей позиции (ядро_en, оговорки, примеры, приёмы) стоит список запрещённых слов, отрицание «не пиши X», перечень артефактов (руки, зубы, искажённый текст) или конкретный предмет из примера, который генератор может утащить в промпт. Справочные ядра (цены, лимиты, даты, параметры вызова) — false. Снять лишние флаги, поставить пропущенные; магнит_причина обязательна при true.
Л8. Споры. Применить решения из реестр_споров (итог «решено: …»): статус решено_по_правилу, противоречия с правилом и решением, текст ядра по решению. Оставшиеся споры: статус спор, обе версии, в примечание «closes by: живой замер / нет данных у Google». Замечания проверяющих вида «спор» (правило применено не в ту сторону) — применить, если доказательство даёт цитата; иначе в вопросы.
Л9. Слияния. Неверные слияния по проверке (продукт + API; разные модели без дословного совпадения; два разных утверждения) → размерджить по частям: одно ядро оставить под старым кодом, второе добавить в конец с новым кодом Я-<тема>-<n+1>…; карта_кодов и коды_старые обновить; связи между ними «уточняет».
Л10. Дубли между темами. Не удалять. У каждого ядра заполнить дом по дубли_между_темами: если дом в другой теме — дом: {тема, код той темы}, и связь «уточняет» на него в связи_с_другими_темами. Если ядро в группе не упомянуто — дом: своя тема, свой код.
Л11. Отрицания в промпте. Ядро Google «describe what you want, not what you don't» — сила рекомендация, магнит true с причиной. Отдельное ядро-факт: «Google's own official examples use short explicit exclusions ("No text.", "Do not change any other elements")» — статус согласовано по кодам примеров, связь «уточняет» между ними. Оба остаются, ни одно не усиливать.
Л12. Порядок блоков промпта. Google обязательного порядка не задаёт; формула из доков дословно, как у Google. Наблюдение «длинные примеры Google часто начинаются с типа кадра / ракурса» — отдельное ядро статус выведено, сила рекомендация, с кодами примеров; не выдавать за правило Google.
Л13. Лицо при правке. Ядро правило_промпта, сила рекомендация: фраза из примеров Google «Keep my face exactly as it is» плюс совет доков описывать критичные детали; источники — коды примеров и E-1-131.
Л14. Слой. У каждого ядра: слой = "промпт", если класс правило_промпта / формула_шаблон или применимость промпт (то, что нужно переводчику промптов); "инструкция", если применимость параметры_вызова или класс процедура / параметр_вызова (то, что нужно агенту, работающему с API и продуктом); "справка" — остальное (факты, лимиты, цены, политика, продукт как описание). Если ядро составное и части попадают в разные слои — слой по главной части, в примечание указать.
Л15. Частично подтверждённые ядра (вердикт «частично»). Текст ядра сузить до того, что подтверждают цитаты; неподкреплённую часть — в оговорку с выведено:true или убрать (в журнал). Замечания «трассировка» у подтверждённых — так же.
Л16. Полнота и переводы. Потерянное при сшивке (вид «полнота») восстановить из частей; неверные переводы (вид «перевод») исправить по оригиналу части.
Л17. Класс. Ядра «модель умеет X» (can / capable / helps you) → возможность_модели, не факт_лимит. Остальные замечания вида «класс» — по определениям ТЗ_СВЕДЕНИЕ.

ПОРЯДОК: прочитать всё по теме → пройти ядра по порядку, к каждому применить линии Л1–Л17 и все замечания проверки → размерджи (Л9) → дом и слой (Л10, Л14) → верхние блоки (матрица_моделей и словарь_терминов пересчитать по ядрам; вопросы: добавить новые, снятые пометить) → журнал → самопроверка.

САМОПРОВЕРКА скриптом: валидный JSON; те же проверки, что в ТЗ_СШИВКА (коды подряд, карта_кодов, E-коды не потеряны против сшито/<тема>.json, кириллица, перечисления, 6 ключей моделей, связи); у каждого ядра есть слой и дом; каждая проблема проверки и каждое предложение статуса по теме имеет запись в журнале; ядра с действует:false имеют заменено.почему.
ОТЧЁТ прорабу (кратко, по-русски): правок применено / отклонено по видам, размерджей, ядер «выведено», «не действует», сколько ядер в слое промпт / инструкция / справка, вопросы.
