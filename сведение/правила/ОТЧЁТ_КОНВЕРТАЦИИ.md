## Отбор (скрипт прораба)

Ядро идёт в конвертацию, если слой «промпт», действует ≠ false и дом — само это ядро. Второй случай — исключение ТЗ: домашнее ядро стоит в другом месте, но оно не в слое «промпт» или не действует. Тогда ядро конвертируется здесь, в паспорт.примечание пишется «home core <код> is not a prompt-layer rule; converted here». Остальные ядра темы идут в <тема>_пропущено.json с причиной по каждому коду. Цепочек, где домашнее ядро само не конвертируется, нет.

## Решения прораба по форме (там, где ТЗ молчит)

1. **id.** `П-<тема>-<n>`: тема полным именем, как в имени файла (`П-камера_свет_композиция-1`). Нумерация идёт в порядке ядер в файле темы.
2. **Механические поля** заполняет скрипт прораба, исполнитель их не меняет: ядро, тема, подтема, unit_kind = класс, derived = (статус «выведено»), target_engine, modality, models, models_partial, паспорт.
   - models: ключи pro/nb2/lite/nb25 со значением «да» (К1).
   - models_partial: ключи со значением «частично», text_en взят из модели_различия; исполнитель сокращает его.
   - Ключи other и не_указано в запись не переносятся. Если models и models_partial пусты, причина пишется в паспорт.примечание.
   - паспорт.связи: коды из связей ядра внутри темы и связей с другими темами, без типов.
3. **strength.** По умолчанию берётся сила ядра. Исполнитель меняет её только по К3 (для derived) и по слабейшей версии (для спор). Каждое изменение идёт в отчёт темы.
4. **caveats_en.** Одна строка на каждую оговорку ядра, с суффиксом « (models: …)», если у оговорки есть модели. Различия моделей со значением «да» из модели_различия (например, иной лимит у nb25) тоже идут в caveats_en: иначе запись с models ⊇ nb25 теряла бы различие. Хедж снимается заменой might → can, сила не меняется.
5. **Приёмы ядер** отдельным полем не переносятся: такого поля в ТЗ нет. В content_en приём попадает, только если он входит в само утверждение ядра. См. вопрос В-1.
6. **Названия функций с «Google»** (Google Search, Google Image Search) в content_en допускаются, только если без них правило теряет смысл. Скрипт выдаёт на них предупреждение, а не ошибку. См. вопрос В-2.
7. **Формат _пропущено.json** (пишет скрипт прораба, не исполнитель): {тема, ядер_в_теме, записей, пропущено_всего, по_причинам, пропущено: [{код, класс, слой, действует, дом, причина}]}. Причины: «слой инструкция», «слой справка», «действует: false (заменено: …)», «дом в другом ядре: <код> (тема …)».
8. **Самопроверка (скрипт прораба)** проверяет всё из САМОПРОВЕРКИ ТЗ и дополнительно:
   - механические поля против ядра;
   - слоты только в формулах, а у формул со слотами есть caveat из К4;
   - у спора есть caveat «disputed: …»;
   - примеры посимвольно совпадают с ядром, их не больше 5;
   - canaries 1–3 только при непустом applies_when;
   - нет терминов с пустым значением;
   - title_en из 3–8 слов;
   - not_applies_when не заполнен при пустом поле в ядре.

   Формулы сверяются так: фрагмент строки от первого до последнего слота должен дословно (с точностью до пробелов и типографских кавычек) стоять в полной цитате одного из источников ядра (извлечение/страницы). Формулы без слотов сверяются по наибольшему дословному совпадению с цитатой и просматриваются глазами.

   После партии 1 проверка дополнена: в названии термина (terms[].термин) не должно быть кириллицы. Три таких метки пришли из ядер: «composition (стр.79)», «system instructions (ноутбук)», «keep-clause (инвариант)». Они возвращены исполнителям и исправлены: пометка снята, её смысл перенесён по-английски в значение_en.
9. **Порядок выпуска.** Исполнитель собирает выход в рабочей папке прораба: скрипт assemble.py, затем самопроверка. Прораб прогоняет свою проверку, копирует файлы в сведение/правила/ и снова проверяет уже там. После этого идёт коммит «правила: <тема>» и сразу push. Непроверенные файлы в репозиторий не попадают.
